# SmartX Review Findings and Patchwork Risks

## Purpose

Explain that this document records review findings from the codex/goal-may26-01 branch. The branch moved SmartX toward capability-aware diagnostics, Smart-aware connection details, profile artifacts, and TUN/DNS visibility, but it also exposed serious patchwork risks.

## Core Diagnosis

State clearly:

SmartX must not become a pile of UI panels and singleton patches. The project needs architecture around controller endpoints, capabilities, profile artifacts, overrides, diagnostics, TUN lifecycle, and Smart core adaptation.

## What the Current Branch Gets Right

Document these positive directions:

- CoreCapability model was introduced.
- More mihomo endpoints were wrapped.
- TUN and DNS config models were expanded.
- Diagnostics dashboard was prototyped.
- Diagnostics report builder was introduced.
- Profile reload artifacts and last-known-good concepts were introduced.
- Smart weights and Smart connection evidence became more visible.
- Connection detail now exposes rule, payload, chain, Smart target, Smart block, ASN, and GeoIP information.

## Critical Patchwork Risks

Document these risks in detail:

1. CapabilityCache is only a cache, not a capability probing system.
2. ApiRequest is becoming a giant endpoint dumping ground.
3. Endpoint result types are inconsistent.
4. API URL and WebSocket URL construction remain string-concatenation based.
5. DiagnosticsDashboardViewController is too large and mixes UI, API calls, formatting, recovery, and maintenance operations.
6. Diagnostics report must not claim to be sanitized unless sensitive data is redacted.
7. ProfileArtifactManager currently copies the loaded source config; it is not a generated effective config pipeline.
8. Last-known-good currently restores a source artifact, not a full runtime state.
9. LightGBM settings are duplicated in Core Settings and Smart Dashboard.
10. Smart Dashboard shows weights but does not yet provide a full Smart decision model.
11. TUN toggle is only a guarded config patch, not a TUN lifecycle.
12. DNS/TUN validation is heuristic and incomplete.
13. AppDelegate remains a giant coordinator and should not absorb more SmartX architecture.
14. Tests do not yet cover the new diagnostics, capability, artifact, endpoint, redaction, and TUN/DNS logic.
15. SmartX identity migration is incomplete; new user-facing text should stop adding ClashX names.

## Honest Terminology Rules

Define naming rules:

- "Generated effective config" may only be used after SmartX has a real config generation pipeline.
- Current copied config artifacts should be called "loaded source copy" or "successful reload artifact".
- "Sanitized report" may only be used after remote URLs, secrets, tokens, credentials, home paths, and process paths are redacted.
- "TUN lifecycle" may only be used after SmartX implements preflight, enable, verify, rollback, disable, and recovery.
- "Smart override" should refer to a persisted SmartX-managed override layer, not only runtime RawConfig mutation.

If a future Codex change creates another large view controller, another global singleton, another direct string-concatenated endpoint, another duplicate settings panel, or another feature that claims more than it actually implements, it should be rejected or split.
