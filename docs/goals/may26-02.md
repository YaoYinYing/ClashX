============================================================
GOAL 1 — Fix ControllerEndpointBuilder scheme boundaries
============================================================

Current issue:

ControllerEndpointBuilder.normalizeExternalBaseURL accepts:
- http
- https
- ws
- wss

That is acceptable for WebSocket base construction, but not acceptable for HTTP endpoint construction.

At the moment, baseHTTPURL() can accept an overrideApiURL with ws:// or wss:// and return it to httpURL(path:), causing Alamofire HTTP requests to use a WebSocket scheme.

Fix this.

Preferred behavior:

- httpURL(...) must only produce http:// or https:// URLs.
- websocketURL(...) must only produce ws:// or wss:// URLs.
- If overrideApiURL is ws://host:port/base, then either:
  A. baseHTTPURL() maps it back to http://host:port/base, or
  B. baseHTTPURL() rejects it as invalidBaseURL.

Choose one behavior and document it in comments.

Recommended implementation:

Use separate normalization helpers:

private static func normalizeExternalHTTPBaseURL(_ baseURL: URL) throws -> URL
private static func normalizeExternalWebSocketBaseURL(_ baseURL: URL) throws -> URL

Rules:

For HTTP:
- http remains http
- https remains https
- ws should either map to http or be rejected
- wss should either map to https or be rejected
- Any other scheme is invalid

For WebSocket:
- http maps to ws
- https maps to wss
- ws remains ws
- wss remains wss
- Any other scheme is invalid

Both helpers must:
- strip user/password
- strip query
- strip fragment
- preserve host, port, and normalized base path
- avoid leaking query token or userinfo into endpoint URLs
- preserve current behavior for ordinary http/https override URLs

Do not break current endpoint-builder smoke cases.

Add smoke tests in:
Tests/SecurityHarness/controller_endpoint_builder_smoke.swift

Required new test cases:

- overrideApiURL = URL(string: "ws://example.com:9090/base")
  - If you choose mapping behavior, httpURL(path: "/configs") must become:
    "http://example.com:9090/base/configs"
  - If you choose rejection behavior, assert that httpURL(path:) throws.

- overrideApiURL = URL(string: "wss://example.com:9443/base")
  - If mapping behavior, httpURL(path: "/configs") must become:
    "https://example.com:9443/base/configs"
  - If rejection behavior, assert that httpURL(path:) throws.

- websocketURL(path:) must still work for ws/wss override bases:
  ws://example.com:9090/base + /traffic -> ws://example.com:9090/base/traffic
  wss://example.com:9443/base + /logs -> wss://example.com:9443/base/logs

I prefer mapping ws->http and wss->https because user configuration may reasonably provide a WebSocket controller URL while HTTP controller endpoints still refer to the same host and port. If this mapping feels unsafe in the current codebase, choose rejection instead, but the test must make the chosen behavior explicit.

============================================================
GOAL 2 — CapabilityCache identity must distinguish changed secrets
============================================================

Current issue:

CapabilityCache.activeIdentity() uses only:
- "secret-set"
- "no-secret"

This avoids leaking raw controller secrets, which is good.

But it fails to distinguish two different secrets. If the secret changes from "old-secret" to "new-secret", identity remains "secret-set", so stale capability statuses may survive after credential changes.

Fix this without leaking the secret.

Preferred implementation:

Add a non-reversible short digest of the active secret.

Example shape:

private func secretIdentityComponent(_ secret: String) -> String {
    guard !secret.isEmpty else { return "no-secret" }
    return "secret-sha256-\(sha256(secret).prefix(8))"
}

Requirements:

- Do not store the raw secret in controllerIdentity.
- Do not log the raw secret.
- Do not include userinfo, query, or fragment from overrideApiURL.
- Changing overrideSecret from "alpha" to "beta" must change currentControllerIdentityForTesting().
- Changing apiSecret from "alpha" to "beta" must change currentControllerIdentityForTesting() when overrideSecret is nil.
- Empty secret must remain distinguishable as "no-secret".

Use CryptoKit if available and compatible with the current deployment target. If CryptoKit introduces compatibility problems for old macOS targets, implement a small non-cryptographic but non-reversible stable hash only for cache identity, and document that it is not a security primitive. Prefer CryptoKit if it builds in Modern CI.

Update:
Tests/SecurityHarness/capability_cache_identity_smoke.swift

Required new test cases:

1. raw secret is not leaked:
   - overrideSecret = "super-secret"
   - identity must not contain "super-secret"

2. different override secrets produce different identities:
   - overrideSecret = "alpha-secret"
   - capture identityA
   - overrideSecret = "beta-secret"
   - call CapabilityCache.shared.reset() if needed
   - capture identityB
   - identityA != identityB
   - neither identity contains either raw secret

3. apiSecret fallback also affects identity:
   - overrideSecret = nil
   - apiSecret = "api-alpha"
   - capture identityA
   - apiSecret = "api-beta"
   - call reset if needed
   - capture identityB
   - identityA != identityB
   - neither identity contains either raw secret

4. no-secret remains no-secret:
   - overrideSecret = nil
   - apiSecret = ""
   - identity contains "no-secret"
