TASK 1: SmartX managed override model
==============================

Problem:
Current LightGBM settings are still mostly runtime/UserDefaults-driven. SmartX needs a persisted, explicit override layer before it can later generate a true effective config.

Implement a minimal SmartX managed override model.

Add a new production file, for example:

ClashX/General/Managers/SmartXManagedOverrideManager.swift

or another location consistent with the project.

Define a Codable model similar to:

struct SmartXManagedOverride: Codable {
    var schemaVersion: Int
    var lightGBM: LightGBMOverride?
}

struct LightGBMOverride: Codable {
    var enabled: Bool
    var modelURL: String
    var autoUpdate: Bool
    var updateIntervalHours: Int
}

Rules:

- Store this file under a SmartX-owned path, not directly inside user remote config.
- Use a namespaced path under the existing config home, for example:
  ~/.config/clash/.smartx/overrides/smartx-managed.yaml
  If YAML encoding is inconvenient with current dependencies, JSON is acceptable for the first PR, but document the choice.
- Do not mutate remote subscription YAML.
- Do not pretend this is a full generated effective config pipeline.
- UserDefaults may remain as a compatibility cache, but the persisted SmartX override file should become the source of truth for LightGBM override settings.
- Add paths in Paths.swift:
  smartXDirectoryURL
  smartXOverridesDirectoryURL
  smartXManagedOverrideURL
- Ensure directories are created before writing.
- Validate modelURL enough to avoid empty or malformed values.
- Clamp updateIntervalHours to a sane minimum, e.g. >= 1.

Bridge behavior:

- Settings.smartLightGBMOverrideConfig, smartLightGBMModelUrl, smartLightGBMAutoUpdate, smartLightGBMUpdateIntervalHours may continue to exist.
- But add a clear load/save sync path:
  SmartXManagedOverrideManager.load()
  SmartXManagedOverrideManager.save(...)
  SmartXManagedOverrideManager.applyToSettings()
  SmartXManagedOverrideManager.captureFromSettings()
- On app startup or first use, if override file does not exist but UserDefaults contains LightGBM settings, migrate them into the override file.
- Settings.syncSmartLightGBMOptionsToCore() should keep working.

Acceptance criteria:

- LightGBM settings are no longer only hidden in UserDefaults.
- Remote configs remain read-only.
- Metadata and docs honestly state that this is managed override groundwork, not full profile generation.

TASK 3: Extract TUN and DNS validators
==============================

Problem:
CoreSettingViewController currently owns TUN/DNS warning logic. That makes it untestable and prevents reuse by future TUN lifecycle and Config Workspace.

Create testable validators.

Suggested files:

ClashX/General/Utils/TunConfigValidator.swift
ClashX/General/Utils/DNSConfigValidator.swift

Define result models similar to:

struct ConfigValidationIssue {
    enum Severity { case info, warning, blocking }
    let severity: Severity
    let message: String
}

struct TunValidationResult {
    let issues: [ConfigValidationIssue]
    var blockingErrors: [ConfigValidationIssue]
    var warnings: [ConfigValidationIssue]
}

struct DNSValidationResult {
    let issues: [ConfigValidationIssue]
}

Move existing Core Settings warning logic into these validators:

TUN:
- include-interface and exclude-interface both set
- strict-route warning
- MTU outside expected range
- udp-timeout <= 0
- route-address / route-exclude-address values that do not look like CIDR
- macOS notes about utun-style device naming if appropriate

DNS:
- fake-ip mode compatibility warning
- respect-rules without obvious resolver path
- prefer-h3 with respect-rules warning
- missing DNS section should be handled as unavailable, not necessarily invalid

Important:
If a check is heuristic, call it heuristic. Do not present weak string checks as strict validation.

Improve CIDR validation if feasible:
- IPv4 CIDR should parse as an IP address with prefix 0...32.
- IPv6 CIDR should parse with prefix 0...128.
- If robust parsing is too large for this PR, keep the heuristic but name it clearly.

Update CoreSettingViewController to consume these validators instead of embedding validation logic.

Acceptance criteria:

- CoreSettingViewController no longer owns TUN/DNS validation logic.
- Validators are pure Swift and testable.
- TUN/DNS warnings can be reused by future TUN lifecycle and config workspace.

TASK 4: Add minimal TUN lifecycle coordinator
==============================

Problem:
Current TUN support is mostly a guarded /configs patch. SmartX needs a named lifecycle boundary even before full embedded TUN support exists.

Create:

ClashX/General/Managers/TunLifecycleCoordinator.swift

or similar.

This coordinator should provide a method like:

func setTunEnabled(_ enabled: Bool, completion: @escaping (TunLifecycleResult) -> Void)

The coordinator should:

1. Check whether the core/controller is running.
2. Read current config state if available.
3. Run TunConfigValidator and DNSConfigValidator.
4. Produce blocking errors if TUN cannot be safely attempted.
5. Preserve previous UI state for rollback.
6. Call ApiRequest.updateTun or its current equivalent only after preflight.
7. Verify state after update if feasible by reloading /configs or current config.
8. Return structured result:
   - success
   - unsupported
   - unauthorized
   - blockedByValidation
   - failed
9. Keep embedded-core TUN explicitly unsupported unless the current architecture truly supports it.
10. Provide recovery text suitable for UI.

Update CoreSettingViewController to call TunLifecycleCoordinator instead of calling ApiRequest.updateTun directly.

Do not build a full TUN editor.
Do not enable embedded core TUN by force.
Do not add root/helper hacks.

Acceptance criteria:

- TUN enable/disable has a named lifecycle path.
- UI distinguishes unsupported, unauthorized, blocked by validation, failed, and success.
- Embedded core TUN remains explicitly guarded.
- Future full TUN lifecycle work has a stable place to evolve.
