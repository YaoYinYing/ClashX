TARGET 1 — Add typed runtime verification model
============================================================

Extend or add a pure Foundation model.

Preferred path:

ClashX/Models/TunRuntimeDiagnostics.swift

ClashX/Models/TunLifecycleDiagnostics.swift

Define typed runtime evidence concepts.

Suggested types:

enum TunRuntimeEvidenceState: String, Codable {
    case notChecked
    case unavailable
    case noTunLikeInterface
    case tunLikeInterfacePresent
    case inconclusive
}

enum TunRuntimeVerificationLevel: String, Codable {
    case controllerConfigOnly
    case interfacePresenceOnly
    case routeVerificationNotImplemented
    case dnsRuntimeVerificationNotImplemented
    case packetFlowVerificationNotImplemented
}

struct TunRuntimeInterfaceEvidence: Codable {
    var interfaceNames: [String]
    var tunLikeInterfaceNames: [String]
    var evidenceState: TunRuntimeEvidenceState
    var message: String
}

struct TunRuntimeVerificationReport: Codable {
    var expectedEnabled: Bool
    var controllerReportedEnabled: Bool?
    var interfaceEvidence: TunRuntimeInterfaceEvidence
    var verificationLevels: [TunRuntimeVerificationLevel]
    var isRuntimeConsistentWithController: Bool?
    var message: String
    var recoverySuggestion: String
}

TARGET 3 — Integrate runtime evidence into TunLifecycleCoordinator
============================================================

Update TunLifecycleCoordinator after controller-config verification.

Behavior:

1. After controller-config verification succeeds or mismatches, collect read-only interface evidence.
2. Produce a TunRuntimeVerificationReport.
3. Include runtime evidence in success / requestedButUnverified / failed messages.
4. If controllerReportedEnabled == expectedEnabled and expectedEnabled == true:
   - if tun-like interface exists, message should say controller config matches and tun-like interface evidence is present.
   - if no tun-like interface exists, message should say controller config matches, but no tun-like interface evidence was found.
   - do not mark it as full runtime failure solely from interface absence unless the code is certain.
5. If expectedEnabled == false:
   - if tun-like interface still exists, warn that interface evidence remains and user may need to inspect controller/core state.
   - do not kill processes or mutate routes.
6. Preserve existing controller config verification.
7. Do not introduce helper-backed TUN.
8. Do not make system evidence a hard requirement for controller-config success unless explicitly safe.

The key idea:

- controller config match remains the primary implemented verification.
- interface evidence is an additional diagnostic layer.
- route/DNS/packet verification remain not implemented.
